# 菌絲體記憶核心設計文件

在既有的 `yazelin/mycelium`（菌絲體）上長出來，名稱沿用（亞澤 2026-11-27：「我們現在有能力把它改成我們現在要的這樣」）。
日期：2026-11-27。狀態：草稿，待亞澤核可。

## 我替亞澤做的決定（請核對）

- private 綁定對象：A 私訊說的事，跟 B 私訊時也不出現。
- Safari 擋公開網頁連本機時，退到 B 就算通過。
- 記憶庫本身不呼叫任何模型；第一版不做向量。
- 不自動合併人物；事實被新事實取代時自動標失效（不刪、可還原、會出現在審閱頁）。

## 一、要做什麼、為什麼

一套記得「人、事、物之間關聯」的記憶庫，讓 AI 回話或寫作時想得起：這個人是誰、跟誰有關、之前發生過什麼、這件事現在還成不成立。

亞澤的原話：「能理清人事物之類關聯……這個記憶查詢資料庫能夠幫助 AI 回想起事情或人物脈絡」「格莉奇以後也許也會換上這個系統，讓他回應得更好」「這樣他們的 agent 也都能變得更聰明、記憶更好」「我們自己在 Larch 上寫小說時應該也要可以用，也不止格莉奇能用，我們人類也能用」。

三種使用者：

1. **agent**：跑在伺服器上、同時回公開貼文與私訊的 AI agent（第一個使用者）、我們自己的 Claude Code／Codex／agy 工作 session、其他人的 agent。透過 MCP 或 HTTP 存取。
2. **人**：亞澤在 Larch 寫小說時查人物、關係、時間線，也能改。透過網頁介面。
3. **其他個人**：裝在自己的 Windows、Mac、Linux 電腦上，接自己的 agent。

為什麼現在做：現有 agent 的人物記憶用顯示名稱當 key，改名就失憶、同名會混；人和人之間沒有連結；私下得知的事沒有標可見範圍。

## 一之二、菌絲體現況與上次的教訓

- 菌絲體（2026-07-22 起）是長篇小說設定工具：角色（含別名）、關係、章節、伏筆、對話紀錄五個陣列，存在每部作品 private repo 的 `data/*.json`；agent skill 可讀、抽候選、直接改、寫前快照、`precheck`／`decisions`／`review`／`graph`。約 4,700 行，零 npm 依賴。
- 教訓一（issue #34）：網頁 app 做好隔天收掉。作者一整天建 21 角色、25 關係、15 章、36 伏筆，全在 agent 對話裡完成，網頁只開兩次。亞澤原話：「我大部份還是跟你討論比較快，完全沒有去開那個網頁。」網頁唯一不可取代的是關係圖。
- 教訓二（README）：AI 一天能生二十幾個角色、三十幾條伏筆，人來不及看；沒看過的設定會被繼續往上蓋。所以要有「只看新改動」的審閱。
- 目前沒有任何作品在用菌絲體，這一版幾乎全新製作，延續的是想法（亞澤 2026-11-27），不做舊資料匯入。想法上沿用：別名合併判斷、寫前快照與還原、precheck、decisions、review、graph、示範角色（林小雨／白衣客等）、「劇情不進公開 repo」的界線。

## 二、目標、非目標、反目標

**目標**
- 以穩定 id 認人（平台帳號 handle 為主），多個稱呼都對到同一人。
- 記錄人、地、物、作品、組織之間的關係與事實，每條事實有生效與失效的時間點；新事實推翻舊的時，舊的標失效、不刪除。
- 每條事實有可見範圍（公開／私下），查詢時依場合過濾。
- 時間軸可以是日期（社交記憶）或章節順序（小說）。
- 單一 SQLite 檔，資料留在使用者電腦，不需要任何雲端服務，也不需要另外準備模型金鑰。
- Windows、Mac、Linux 都能一行指令裝起來。
- 公開 repo，格莉奇是第一個正式使用者。

**非目標（這一版不做）**
- 自動寫小說的平台功能（依世界觀自動產章節）。記憶庫要能支撐它，但寫作流程以後再做。
- 向量搜尋。這一版用名稱比對、全文搜尋、關係走訪；向量做成以後可選裝的模組，結構預留欄位。
- 多人共用的雲端服務、帳號系統。
- 跨使用者或跨 agent 的人物合併（例如格莉奇認識的某人與 Mori 認識的某人算不算同一個）。

**反目標（做出來會被當失敗的情況）**
- 私下的事出現在公開查詢結果裡。
- 系統自己把兩個不同的人合併，而且事後看不出、還原不了。
- 資料被送到使用者沒設定的外部服務。
- 要求使用者先申請某家模型的 API 金鑰才能用。

## 三、限制

- 執行環境：Node 22.13 以上（內建 `node:sqlite`，不需要編譯原生模組）。已實測 Node 22.17 內建 SQLite 3.50，FTS5 與 trigram 分詞可用；trigram 查詢至少三個字，兩個字的名字改用 `LIKE` 比對。`node:sqlite` 在 Node 22 會印 ExperimentalWarning，啟動時要壓掉。
- 不用需要編譯的套件（better-sqlite3、sqlite-vec 等），確保 Windows／Mac 不必裝編譯工具。
- 授權：MIT，`Copyright (c) 2026 林亞澤 (Yaze Lin)`。
- 網頁介面是公開專案的前端，要加亞澤的推廣 footer（promo-footer 四件套）。
- 介面文字、文件用正體中文；README 另附英文段落讓外國使用者看得懂。
- 依賴與安裝腳本都放在這個 repo 裡。
- git 流程：短命 branch、PR、auto-merge。

## 四、做法比較（已決定）

**規模（亞澤選甲，再改成直接公開）**
- 甲：只改格莉奇，結構照通用版設計。
- 乙：先做共用服務。
- 決定：開獨立公開 repo，核心做成通用；第一個使用者是格莉奇。跨 agent 的服務化以後再做。

**現成方案 vs 自己做**（研究報告：本 session scratchpad，2026-11-27）
- Graphiti：時效、去重最完整，但每筆寫入要多次呼叫模型、要圖資料庫、提示詞英文。
- Mem0 開源版：已移除關係圖。
- LightRAG／Cognee：偏向文件。
- 決定：自己做，借 Graphiti 的「事實有生效／失效時間、矛盾時標失效不刪除」，借 memobase 的「批次整理」，資料存 SQLite。

**介面怎麼連資料（亞澤選 A，B 備案）**
- A（主要）：本機程式提供 MCP 與本機 HTTP，網頁介面放 GitHub Pages，連使用者自己的 `127.0.0.1`。
- B（備案）：同一份介面檔案由本機程式自己在 `localhost` 提供，離線可用。
- C（排除）：資料庫整個放瀏覽器裡，agent 讀不到。

**儲存與同步（亞澤 2026-11-27 同意）**：主本是「操作紀錄」，SQLite 是由操作算出來的查詢用資料庫。
- 每次寫入（建立人事物、加別名、記事實、標失效、合併、還原合併、改名稱或摘要、記原始紀錄）同時寫成一筆操作：全域唯一 id（ULID）、裝置 id、混合邏輯時鐘時間戳、操作種類與內容。
- 小說作品的 private repo 放 `ops/<裝置名>-<裝置id>.jsonl`，每台裝置只追加自己的檔，git 不會有合併衝突。SQLite 檔不進 git，可從 ops 整個重建。
- `sync`：拉 → 把沒套用過的操作依時間戳（同時間比裝置 id）重播 → 推自己的檔。重播必須冪等，同一筆操作套兩次結果不變。
- 合併規則：事實與原始紀錄只新增，聯集；標失效冪等；人事物的名稱、摘要逐欄位以時間戳較晚者為準，被蓋掉的值進審閱頁；同一人物被不同裝置合併到不同對象時，兩邊都保留、標「待決定」放進審閱頁，由人選。
- 不採用：直接同步 SQLite 檔（會互相覆蓋或損壞）；cr-sqlite（原生模組）；node:sqlite changeset（逐列寫衝突處理、二進位不好查）。
- git 保護（亞澤 2026-11-27 同意）：ops 目錄是一個 git 工作目錄，每次寫入後自動在本機 commit（不推），sync 時才推。還沒 sync 的操作也有本機歷史可退。任何時間點的狀態都能用「重播到該時間點」還原，原本菌絲體的寫前快照由此取代。
只有一台裝置的使用者不必 sync，但寫入同樣記成操作，備份與搬家就是複製操作檔；要推到遠端時建議用 `--require-private`。

**抽取由誰做（我的決定）**：記憶庫本身不呼叫任何模型。由呼叫它的 agent 自己讀對話、決定要記什麼，再呼叫工具寫入。所以使用者不用準備金鑰，也不會多花錢。

## 五、資料結構

一個 SQLite 檔可以有多個**空間**（space），彼此不互通。

- `spaces`：id、名稱、種類（`social` 社交記憶／`story` 小說）、時間軸種類（`date`／`chapter`）、章節清單（story 用，見下）。
- `entities`：id（ULID）、space、類型（person、place、item、work、org、event、concept）、正式名稱、一段摘要、建立與更新時間、`merged_into`（被合併時指向保留的那個）。
- `aliases`：entity_id、稱呼、平台（larch、line、youtube……可空）、是否為帳號 handle、來源 fact／episode、建立時間。同一 space 裡一個 handle 只能對一個 entity。
- `facts`：id、space、主體 entity、謂語（自由文字，如「室友」「喜歡」「答應要」）、客體（entity、文字、或另一條 fact，三擇一）、`valid_from`、`valid_to`（空＝仍成立）、可見範圍（`public`，或 `private` 加上「屬於哪段對話」的對象 entity id，見第六節可見範圍規則）、來源（episode id 或「手動」）、信心、建立者（agent 名稱或人）、`superseded_by`。
- `episodes`：原始紀錄，只追加不改：時間、來源（例：「larch 私訊」「茶館留言」「第 5 章」）、可見範圍、內文或摘要、相關 entity id。用來追查「這條事實從哪來」。
- `merges`：每次合併記一筆（誰、何時、哪兩個、為什麼），可還原。
- `vectors`（預留，這一版不建索引）：對象 id、模型名稱、向量 blob。
- FTS5 trigram 索引：entities 名稱與摘要、aliases、facts 的謂語與文字、episodes 內文。

**時間軸**
- `date`：ISO 日期時間。
- `chapter`：space 裡存一份有序章節清單（例：`["序章","ch01","ch01-s2","ch02"]`），`valid_from`／`valid_to` 存章節 id，比較時用清單順序。
- 小說的「誰知道什麼」：用 fact 表示，主體是角色、謂語「知道」、客體是另一條 fact，有自己的生效章節。

## 六、寫入與查詢

**寫入工具**（MCP 與 HTTP 同一組，名稱暫定）
- `log_episode`：記一筆原始紀錄。
- `upsert_entity`：建立或更新人事物；回傳可能重複的候選（同名、同別名、全文相近）讓呼叫者判斷，系統不自動合併。
- `add_alias`：加稱呼或帳號。
- `remember`：記一條事實，可附來源 episode。若同主體、同謂語已有仍成立的事實，回傳這些讓呼叫者決定是否用 `invalidate` 讓舊的失效。
- `invalidate`：把某條事實標成在某時間點失效，可指定取代它的新事實。
- `merge_entities`：合併兩個人事物，寫入 `merges`，可用 `unmerge` 還原。

**查詢工具**
- `recall`：輸入一段文字（例如這次收到的訊息）或指定的人名、時間點（日期或章節）、可見範圍上限。
  1. 用別名表在文字裡找出提到的人事物（逐一比對所有別名，資料量小直接掃）。
  2. 取這些人事物在該時間點仍成立、可見範圍允許的事實。
  3. 往外走一到兩層關係，帶出相關的人。
  4. 全文搜尋補上相關的 episode。
  5. 回傳兩種格式：給模型直接放進提示詞的一段中文，以及結構化 JSON。
- `get_entity`、`search`、`timeline`（某人或某 space 依時間排序的事實）、`neighbors`。

**可見範圍規則**（我的決定，比原規則更嚴）：`private` 綁定對象。`recall` 一定要帶場合：公開場合只回 `public`；跟某人私下對話時，回 `public` 加上「綁定對象就是這個人」的 `private`。A 私訊說的事，跟 B 私訊時也不會出現，走關係帶出 A 時也一樣。沒帶場合就當公開。episodes 同樣帶可見範圍與對象。

## 七、程式與介面

- **核心模組**：資料表、寫入、查詢、可見範圍過濾，純 Node、無外部依賴。
- **CLI**：`npx github:yazelin/mycelium <指令>`
  - `mcp`：用 stdio 跑 MCP server，給 Claude Code 等 agent 接。
  - `serve`：跑本機 HTTP（預設只綁 `127.0.0.1`），同時提供 B 備案的介面頁。
  - `import`／`export`：JSONL 匯入匯出，備份與搬家用。
  - `sync`：跟作品的 private repo 交換操作紀錄（見第四節的儲存與同步）。
  - `init`：建立資料檔與 space。
- **HTTP 安全**：啟動時產生一組存取碼並印出，網頁第一次連線時貼上（存在瀏覽器 localStorage）。CORS 只允許 GitHub Pages 的網域與 localhost，並回應瀏覽器私有網路存取的預檢標頭。伺服器模式要明確指定綁定位址才會開放對外。伺服器上的資料庫建議只綁本機，要看時用 SSH 通道接到自己電腦，以 B 模式的頁面瀏覽。
- **主要入口是 agent**（教訓一）：MCP 工具與菌絲體 skill 涵蓋所有讀寫；人透過跟 agent 對話來查、改。
- **網頁介面（GitHub Pages，A；B 備案）只做對話給不了的事**，範圍刻意小：
  - 連線設定（位址、存取碼）；連不上時顯示示範資料並說明怎麼安裝。
  - 關係圖：以選定的人為中心一到兩層；story space 有章節滑桿，拖到某章看當時的關係與誰知道什麼。
  - 審閱頁：只列上次看過之後新增、失效、合併的紀錄（沿用 review 的作法），每筆可一鍵標失效或還原合併。
  - 單一人事物頁（從圖或審閱頁點進去）：別名、仍成立的事實、已失效的事實（灰色）。
  - 不做表單式的大量編輯；編輯走 agent。
  - 頁尾推廣 footer。
- 預設資料檔位置：使用者家目錄下的 `.mycelium/mycelium.db`，可用參數或環境變數改。

## 八、第一個 agent 的接入

第一個接入的 agent（同時回公開貼文與私訊）有自己的私人設計文件，不放在公開 repo。這裡只要求：公開回覆查詢時只帶 `['public']`，私下對話帶 `['public','person:<對方>']`；場合由程式判定，不交給模型。

## 九、驗收

- 單元測試：寫入、失效、合併與還原、時間點查詢、章節順序、可見範圍過濾。
- 同步測試：兩個裝置各自離線寫入後交換，結果必須相同且與順序無關；重播兩次結果不變；兩邊合併同一人到不同對象時出現「待決定」；從 ops 重建的 SQLite 與原本的查詢結果一致。
- 私訊洩漏測試：同一人有 private 事實時，公開 `recall` 的結果裡一條都不能出現（負控制）。
- 回想評測集：至少 20 題「看到這句話，該想起誰、哪條事實」，另含「不該想起」的反例；格莉奇切換前後各跑一次。
- 跨平台：GitHub Actions 在 ubuntu、windows、macos 上跑測試與 `npx` 安裝。
- 網頁：每個按鈕、搜尋、編輯、合併、章節滑桿都實際操作過。Chrome 要能走 A；Safari 若擋公開網頁連本機 HTTP，退到 B（`serve` 在本機提供同一份頁面）就算通過，不為 Safari 做本機 HTTPS（我的決定）。
- 私訊洩漏測試另加一組：A 的私事不能出現在跟 B 的私下查詢裡。

## 十二、可見範圍標籤與未來的公司內部系統（亞澤 2026-11-27）

- 可見範圍統一成一個標籤 `audience`：`public`、`person:<人>`，以後可加 `group:<群組>`、`role:<角色>`。查詢時呼叫者帶「能看哪些標籤」，紀錄的標籤在其中才回傳。前文的 public／private 與「私下綁定對象」都以此表示（private 綁某人＝`person:<那人>`）。
- 未來方向（不在本設計範圍）：公司內部系統的記憶（知識庫、ERP 客戶與訂單、LINE bot 紀錄）也用這套管理，讓 AI 查得到人、事、物與時間線的關聯，再自行推論出洞見。公司內部系統 是 Python，可透過 MCP／HTTP 呼叫，或直接讀操作紀錄（每行一筆 JSON）。屆時另寫設計：群組與角色權限怎麼對應 公司內部系統 既有的三層權限、資料量與來源的匯入方式。
- 已知限制：實體（人物）的名稱、摘要與合併視為公開資訊，不帶 audience；只有別名（alias）帶 audience。私下得知的同一人關係（例如「甲其實就是乙」）不寫進摘要或合併，改用帶 `person:<id>` 標籤的事實記錄。
- 寫入也照可見範圍（2026-11-27 總審查後補）：
  - 較窄的範圍不能改動較寬的事實：寫入範圍為 W、被取代或失效的事實範圍為 T，只有 W＝T（`person:` 經 resolve 後比）或 W＝`public` 才允許，否則拒絕且不寫入。`invalidate` 加選用 `audience`（預設 `public`）。
  - `remember` 回傳的同類仍成立事實，主體用 resolve 後的人比對，只回傳 `public` 或與這次寫入同一範圍的。
  - `upsert_entity` 加選用 `audiences`（預設 `['public']`），重複候選只比對看得到的別名。
  - 查詢輸出的 `superseded_by`、`source_episode`、`object_fact` 指向看不到的紀錄時清成 null（只清輸出，不動資料庫）。
- 資料庫格式有版本號（`user_version`，目前為 2）；與程式不符就清空重建資料表，再從操作紀錄重播。
